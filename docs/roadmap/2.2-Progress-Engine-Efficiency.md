# Progress Engine Efficiency Roadmap

Date: 2026-10-26
Scope: How challenge runs and achievements are recalculated when users add, edit, or delete saves, seasons, trophies, and career stints.

## Current State (before this roadmap)

- Two engines run inline in API requests:
  - Challenges (`src/lib/db/challenges.ts`): `addChallengeForTrophy` re-evaluates every published challenge against the save's trophies; `addChallengeForTeam` / `addChallengeForCountry` create empty runs.
  - Achievements (`src/lib/db/achievements.ts`): `evaluateAchievementsForUser` runs count aggregates and upserts one row per achievement.
- Triggers: save create, career stint create, season create/update (via `addTrophyToSave`), trophy create/update.
- Not triggered: trophy delete, season delete, save delete, career stint edit/delete → progress goes stale.
- Hot spots:
  - `evaluateAchievementsForUser` re-seeds the whole catalog on every call (~24 writes) and is called once per upserted challenge run.
  - `upsertCareerChallenge` writes every goal row individually, evaluates achievements, and re-loads the full run with includes nobody uses.
  - Adding one trophy can issue hundreds of queries; seasons with several wins run these chains in parallel and race on unique keys.

## Steps

- [x] **1. Single recompute entry point per save**
  - `recomputeSaveProgress` in `src/lib/db/progress.ts` loads trophies, challenge definitions, and existing runs once, evaluates in memory, writes only runs/goals whose state changed, then evaluates achievements once.
  - All mutations call it: save create, career stint create/update/delete, season create/update/delete, trophy create/update/delete. Save delete re-evaluates user-level achievements.
  - Season create/update creates all trophies first (`skipProgress`) and then runs one recompute instead of one per trophy.
  - Achievement evaluation skips upserts when progress / unlock state did not change.
  - Edit/delete events (`trophy.updated`, `trophy.deleted`, `season.updated`, `season.deleted`, `save.deleted`, `career.updated`) evaluate every achievement; additive events only evaluate their triggers unless challenge runs changed.
  - Team/country challenges still get an empty run when a save or stint starts at a matching team/country (`ensureForTeamIds` / `ensureForCountryCodes`), but goals are now evaluated against existing trophies instead of always starting at 0.
  - `ABANDONED` runs are left untouched.
  - Measured on dev (save with 6 trophies, 38 published challenges): challenge sync = 5 queries, full recompute = 20 queries, 0 writes when nothing changed. Before: one trophy triggered ~24 seed writes plus dozens of queries per challenge run.
- [x] **2. Stop seeding achievement definitions at runtime**
  - Removed `seedAchievementDefinitions()` from `evaluateAchievementsForUser` and `GET /api/achievements`.
  - Definitions must be seeded on deploy / catalog change with `npm run achievements:seed`.
- [x] **3. Cache challenge definitions**
  - `getAllChallenges()` in `src/lib/db/challenges.ts` now holds an in-process, in-memory cache (5 minute TTL) instead of hitting Postgres on every call.
  - Chose in-memory over Redis: `ChallengeDefinition` has `DateTime?` fields (`publishedAt`, `archivedAt`, `createdAt`, `updatedAt`) that would silently become strings after a Redis JSON round-trip, and the shared `readThroughCache` helper doesn't deserialize dates back. In-memory keeps real `Date` objects with no extra risk.
  - Definitions only change at runtime via the offline `npm run challenges:seed` script (`seedChallengeCatalog()`), which now calls `invalidateChallengeCatalogCache()` after writing. This busts the cache in-process; cross-process invalidation (seed script vs. running server) isn't attempted since they're separate processes anyway — new deploys get fresh processes, local dev just waits out the TTL or restarts.
  - Cleaned up dead code left over from the step 4 refactor (`getTeamMatchingChallenges`, `getCountryMatchingChallenges`, `getCompetitionMatchingChallenges`, `getChallengesForSave`, `checkForMatchingChallenges`) that had no remaining callers.
- [x] **4. Remove side effects from the challenge upsert**
  - `upsertCareerChallenge`, `addChallengeForTrophy`, `addChallengeForTeam`, `addChallengeForCountry` and `addNewEmptyCareerChallenges` were replaced by `syncChallengeRunsForSave` + internal `writeChallengeRun`.
  - Run writes no longer evaluate achievements or re-load the full run; they return `created` / `updated` / `unchanged`.
  - New runs are created with nested goals in one upsert (race-safe on the unique key); existing runs update in one transaction with bulk goal inserts and only changed goal updates.
- [ ] **5. Stable run timestamps**
  - Partially done as part of step 1/4: `startedAt` is only set on creation and `completedAt` is preserved while the run stays complete.
  - Remaining: per-goal `completedAt` evidence (which trophy completed the goal).
- [x] **6. Reliable post-response work**
  - Replaced `runSideEffectsWithBudget`/`runSaveSideEffectsWithBudget` (1.2s `Promise.race` against a timeout, where losing the race left work running against a possibly-frozen/recycled instance) with `runAfterResponse`, built on Next's stable `after()` API (`src/app/api/saves/[id]/seasons/route.ts`, `src/app/api/saves/route.ts`).
  - `after()` schedules the callback to run once the response is sent but keeps the function instance alive until it settles, bounded by the route's `maxDuration` rather than a fixed timeout — so progress recompute reliably finishes instead of racing a clock.
  - Added `export const maxDuration = 30;` to both routes as headroom for the `after()` work (measured recompute cost is ~20 queries / ~1s, well under this).
  - Other mutation routes (trophy update/delete, career stint update/delete, career update, season delete, save delete) already awaited `safeRecomputeSaveProgress`/`safeRecomputeUserProgress` synchronously before this change; left as-is since they weren't using the racy budget pattern — only the save/season creation paths used it.
- [ ] **7. Serialize per-save progress work**
  - Season flows are serialized (step 1). Remaining: guard concurrent requests for the same save (e.g. advisory lock or outbox).
- [ ] **8. Decide achievement unlock semantics**
  - Today an unlocked achievement keeps `unlockedAt` even if live progress drops below the threshold. Confirm and document.
